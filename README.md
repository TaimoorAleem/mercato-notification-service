# Mercato — Notification Service

Order confirmation email service for **Mercato**, a distributed e-commerce platform. Consumes `OrderPlacedEvent` messages from Kafka and sends a confirmation email to the customer.

Part of a multi-repository project — see the [API Gateway repository](https://github.com/TaimoorAleem/api-gateway) for the system overview and links to the other services.

---

## Role in the System

This is the only purely event-driven service in the platform. It exposes **no HTTP API**, is not routed through the API Gateway, and nothing calls it — it only listens.

```
order-service ──▶ Kafka ──▶ notification-service ──▶ SMTP (Mailtrap)
    :8081      order-placed-      :8087
                  event
```

That decoupling is the point: order placement completes as soon as the event is published. Email delivery is slow, external, and failure-prone, so keeping it off the request path means a flaky SMTP provider can never make `POST /api/order` slow or fail.

The trade-off is that this service is entirely downstream. It has no database, no state of its own, and no way to be triggered other than by an event appearing on the topic.

---

## What It Does

`NotificationService.listen` is a single `@KafkaListener` on the `order-placed-event` topic. For each event it composes a plain-text email:

```
Subject: Your Order with OrderNumber <orderNumber> is placed successfully
From:    mercato@email.com
To:      <event.email>

Hi <firstName> <lastName>,

Your order with order number <orderNumber> is now placed successfully.

Best Regards,
Mercato
```

and sends it through `JavaMailSender`. On a `MailException` it logs the error and rethrows as a `RuntimeException`.

That rethrow matters for delivery semantics: because the exception propagates out of the listener, the offset is not committed and Spring Kafka's default error handler retries the record before eventually giving up. There is no dead-letter topic configured, so a permanently failing message is ultimately logged and dropped.

Delivery is **at-least-once** — a mail that succeeds but whose offset commit fails will be re-sent. There is no idempotency key or de-duplication.

## The Shared Avro Schema

This service holds a copy of `order-placed.avsc` that is **byte-identical** to the one in `order-service`, including the namespace `com.taimoor.order_service.event`:

```json
{
  "type": "record",
  "name": "OrderPlacedEvent",
  "namespace": "com.taimoor.order_service.event",
  "fields": [
    { "name": "orderNumber", "type": "string" },
    { "name": "email",       "type": "string" },
    { "name": "firstName",   "type": "string" },
    { "name": "lastName",    "type": "string" }
  ]
}
```

The generated `OrderPlacedEvent` class therefore lands under `src/main/java/com/taimoor/order_service/event/` — a package named after the *producing* service, which is why that path looks out of place in this repository. It is generated by `avro-maven-plugin` during `generate-sources`, not hand-written.

The consumer is configured with `specific.avro.reader=true`, so `KafkaAvroDeserializer` resolves the writer schema from the Schema Registry and deserialises directly into this specific record rather than a `GenericRecord`.

**Both copies of the `.avsc` must be kept in sync.** They are duplicated across repositories rather than shared through a common artifact; a change on one side without the other will break deserialisation at runtime.

Note that the Avro fields deserialise as `CharSequence` (`Utf8`), not `String` — hence the `.toString()` on the email address in the listener.

## Getting Started

### Prerequisites

- Java 21
- Maven (or the bundled `./mvnw`)
- **A running Kafka broker and Schema Registry** — this repository has no `docker-compose.yml`. That infrastructure is owned by [`order-service`](https://github.com/TaimoorAleem/order-service); start it there first:

  ```bash
  cd ../order-service && docker compose up -d
  ```

  This provides Kafka on `9092` and the Schema Registry on `8085`.
- An SMTP account. The defaults target [Mailtrap](https://mailtrap.io) sandbox, which captures mail instead of delivering it — the right choice for a project that emails whatever address a test user happens to have.

### 1. Create `.env`

```bash
cp .env.example .env
```

```properties
MAIL_HOST=sandbox.smtp.mailtrap.io
MAIL_PORT=2525
MAIL_USERNAME=<your mailtrap username>
MAIL_PASSWORD=<your mailtrap password>
```

`MAIL_HOST` and `MAIL_PORT` have defaults in `application.properties`; **`MAIL_USERNAME` and `MAIL_PASSWORD` do not** and must be supplied or the application will not start.

### 2. Run the service

```bash
./mvnw spring-boot:run
```

The service starts on `http://localhost:8087` (the web server is only there to host the actuator/servlet context — there are no application endpoints) and joins consumer group `notificationService`.

### 3. Verify

Place an order through `order-service`, then watch this service's logs:

```
Got message from order-placed topic: {"orderNumber": "...", "email": "...", ...}
Order Notification email sent!
```

The message itself should appear in your Mailtrap inbox. You can also inspect the topic directly in Kafka UI at `http://localhost:8086`.

To publish a test event without going through the order flow, use Kafka UI's producer with the registered Avro schema — a raw JSON produce will not deserialise, since the consumer expects Avro with a Schema Registry magic byte.

## Configuration

`src/main/resources/application.properties`:

| Property | Value |
|---|---|
| `server.port` | `8087` |
| `spring.mail.host` | `${MAIL_HOST:sandbox.smtp.mailtrap.io}` |
| `spring.mail.port` | `${MAIL_PORT:2525}` |
| `spring.mail.username` / `password` | `${MAIL_USERNAME}` / `${MAIL_PASSWORD}` (required) |
| `spring.kafka.bootstrap-servers` | `localhost:9092` |
| `spring.kafka.consumer.group-id` | `notificationService` |
| `spring.kafka.consumer.value-deserializer` | `io.confluent.kafka.serializers.KafkaAvroDeserializer` |
| `spring.kafka.consumer.properties.schema.registry.url` | `http://127.0.0.1:8085` |
| `spring.kafka.consumer.properties.specific.avro.reader` | `true` |

`.env` is loaded via `spring.config.import=optional:file:.env[.properties]` and is gitignored — only `.env.example` is committed.

## Testing

```bash
./mvnw test
```

`NotificationServiceApplicationTests` is a context-load test. `TestcontainersConfiguration` supplies a Kafka container (`apache/kafka-native:latest`) via `@ServiceConnection`, so the listener's consumer factory has a broker to connect to. There is no test that asserts an email is composed or sent.

`TestNotificationServiceApplication` runs the app against Testcontainers-managed Kafka:

```bash
./mvnw spring-boot:test-run
```

Docker must be running for either. Note the Testcontainers setup provides Kafka but **not** a Schema Registry, so it cannot exercise Avro deserialisation end to end.

## Known Limitations

- **The Avro schema is duplicated**, not shared. Keeping it in sync with `order-service` is a manual discipline.
- **No dead-letter topic.** A permanently failing message is retried and then dropped with only a log line.
- **No idempotency.** At-least-once delivery means a redelivered event sends a duplicate email.
- **Hardcoded sender and branding** — the `From` address (`mercato@email.com`) and the sign-off are baked into the listener rather than being configurable.
- Plain-text emails only; no HTML template, no localisation.
- Order confirmation is the only notification type — there is no order-shipped, order-cancelled, or any other event handled.
- No test covers the actual notification behaviour.
